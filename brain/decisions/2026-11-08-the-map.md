# ADR 2026-11-08 — Mahoraga is a dated map of where local AI has caught up with cloud AI

## Status
Accepted (2026-11-08), except decision 3, which is proposed until Kaito rules on it.

**Refines:** `2026-10-29-long-term-study.md`. Its five conditions for pooled results still
stand, as does its rule that routing comes last. **Reverses:** part 4 of
`2026-11-08-optiplex-bench-host.md`, which declined Sonnet and Haiku in the monthly cloud pass.

## Context

On 2026-11-08 Kaito asked for the portfolio page and the README to be redone, and said the
local app had made Mahoraga look like an app when it is a study. He then said what the study
is for. It isn't about whether a reader should stay on the cloud or switch to local. He is
looking for where local models can beat cloud models, a little more as time goes on, in any
kind of work. He meant capability (what a model on owned hardware can do), not compliance
(where the cloud isn't allowed).

Four facts shaped the decision.

**1. Every row measured so far says local hasn't caught up.** On the 47 tasks from attrs and
more-itertools, aider and qwen3.5 on the 16 GB laptop resolved 17 and Claude Code on Opus 5.5
resolved all 47, at $0.21 a task. At what the cloud spent on the tasks local solved, local
would need 95% to break even.

**2. The gap depends on the kind of task.** The same-agent run on 11-08 (Claude Code driving
qwen3.5 on the Studio, not yet published) resolved 16 of 17 more-itertools tasks and 8 of 19
attrs tasks, while the cloud resolved all of both. Small, self-contained functions came close
and class machinery did not. Which kinds of work have crossed is a question no leaderboard
answers, since leaderboards rank models on one mix of tasks.

**3. A search for wins finds wins.** Across enough kinds of work, metrics and slices, a local
win will turn up by chance, or by picking the metric that flatters local. The project's
credibility comes from publishing a 30-0 loss.

**4. The study code is already apart from the app.** `agentbench/` and `audit/` import only
`version` and `config` from the rest of the package, while the app side (routing, the service,
the demo and the CLI command) imports the study in four places.

## Decision

1. **Mahoraga is a dated map of where local AI has caught up with cloud AI.** A row is one
   kind of work, with local and cloud measured on the same tasks. A crossover, meaning a row
   where local has caught up, is the headline event, and between crossovers the story is the
   gap and how fast it moves. The map publishes every row, losses included, and what counts
   as caught up is fixed before a run.
2. **Caught up means the low end of local's 95% interval clears the break-even rate** against
   what the cloud spent on the same tasks. It is the verdict's existing line, so every row
   reads on one scale, and a row can't be declared caught up by choosing a friendlier metric.
3. **Proposed: a kind of work joins the map only with a mechanical check and real tasks.** The
   check is something that marks an answer right or wrong without a model or a person judging
   it (a repository's tests, an exact answer, labelled fields, word error rate against a
   transcript). The tasks come from real work, not a public benchmark, since public
   benchmarks are likely in both sides' training data. A model never grades another model's
   answer, because the cloud would be grading its competitor. HumanEval+ stays off the map
   for this reason.
4. **The cloud side is every tier.** Opus 5.5, Sonnet 5.5 and Haiku 5.5 run the same tasks, so
   a row says which tier local has caught up with. Against Opus alone, the first crossover
   would wait for local to match the best model there is. The cheaper tiers are what much
   routine work runs on. `night/2026-11-08-cloud-tiers.sh` on the OptiPlex runs Sonnet and
   Haiku on the published 47, and `monthly-cloud.sh` runs all three on new tasks.
5. **The README is the study, and the app is documented apart.** The local app, the HTTP API,
   the MCP server and the router moved to `docs/app.md`, and the README links to it once. The
   stay/split/switch verdict stays as the reader's tool for placing their own repository on
   the map, but it no longer leads.
6. **Splitting the app into its own repository is the better architecture, and it waits.**
   Kaito chose the docs first. The study has different readers and a different lifecycle (a
   CLI and dated results) from the app (a service with its own API and callers), and fact 4
   above makes the split mostly packaging. It gets its own decision once the docs pass shows
   nothing else reaches across.
7. **The site follows the map.** Research leads with the map, Engine becomes Method (the
   check, mining, the commit-date split, the break-even line), and Install becomes Replicate.
   The `/portfolio` description follows the new hero.

## Alternatives considered

- **Keep stay/split/switch as what the project is.** Rejected by Kaito, because the verdict
  answers a reader's buying question while the study asks where local stands.
- **Publish only the wins.** Rejected, since publishing only local's wins would cost the
  study the trust its losses earned.
- **Compare against Opus alone.** Rejected, for decision 4's reason.
- **Split the repository now.** Deferred, since the docs pass is reversible and shows whether
  anything still crosses the line between the study and the app.

## Consequences

- A row that says local has caught up names the cloud tier, the machine, and the tasks it
  covers, and it carries the commit-date split, since a small model that remembers a popular
  library is the likeliest false crossover.
- The same-agent row and the cloud tiers fill the next rows of the map. The 92-task row needs
  the cloud arm on click's tasks before it has a cloud column.
- A positive control would show the method can return "caught up" when it is true. Every row
  so far says cloud wins, so a kind of work where local is plausibly level already (speech to
  text graded by word error rate, for example) is worth measuring early.
- `CLAUDE.md` describes the project this way and points here.
